Embedded tools grounded in what the chip actually does.

Dulse is a series of open-source tools to help make embedded development reliable, even when using questionable code coming from LLMs. Dulse builds hardware contracts from vendor documentation, hardware tests, and errata to catch common hardware errors before you ever flash them to a chip.

A contract with time in it

The control loop's deadline is a term the compiler holds, not a comment.

A task says how often it runs and how late it may be. The period isn't trusted from the source: it's derived from the timer's PSC and ARR writes, the APB prescaler and the clock tree the program set up, and a mismatch is an error. The response time is the task plus everything that can delay it: the longest interrupts-off span, every more urgent handler once per period, and the flash.

// pwm-rc-loop/src/main.dul (NUCLEO-F429ZI, PI loop on an RC circuit) task fn control() every 1ms deadline 100us on TIM6 { ... } // dulsec time . --> control: period 1 ms (PSC 89, ARR 999 at 180 MHz), response 3.2 µs, PASS

The flash is the one people forget. On an STM32F4 a sector erase stalls every fetch from that bank for up to 2 s, so a settings save in main is a 2 s masked section as far as every handler in flash is concerned. The inverted pendulum port steps every 25 µs. The build refuses the image and names the fix.

One line does the same over a C image: [deadlines.TIM2_IRQHandler] period = true in an annotation file, and the erase inside a library, C or Dulse, gets the error with its file and line.

dulsec build .pendulum port, F429
error E1210: deadline of `step` not met: the erase of sector 7 (128 KB, PSIZE x32) in `params::save` (src/params.dul:351:5, from `main`) stalls every flash fetch for up to 2 s, against 25 µs; met when `step` and what it calls run from RAM (`[mpu] exec_ram`: 41 functions, 5212 bytes; no check is weakened), or when the erase can't run while control::MODE is outside {Idle, Fault} (the modes requirement C.STEP gives this deadline)

F4 flash: the deadline is held against the printed maximum; the bench measured 204 ms on an F401. A handler in RAM with the erase loop still in flash was blocked just the same, which made the rule stricter.

Fine print: cycle tables are calibrated on the F303 and F429 and nowhere else yet, so a verdict elsewhere is tested rather than proved. No deadline miss has been caught on code we didn't write and confirmed on silicon; the pendulum and the RC loop are ours.

The arms

One checker, several things to point it at.

Check

Any Cortex-M ELF, any toolchain. Reads and reports, alters nothing.

foundThe CubeL5 typo above. Microchip's HAL read-modify-writing the write-only SUPC_CR, core-off bit included. The SAMD21 XOSC32K.AAMPEN erratum in nine Zephyr board files. Four in ChibiOS master's HALs, e.g., the G4 'boost' option writes the bit that turns boost off, so the part runs 170 MHz in the 150 MHz mode (read back on a NUCLEO-G474RE). None filed upstream yet.

gapPrecision on vendor code is 0.06 to 0.16 per site held out; recall on historical bugs 1 to 3 in 46. See 'what it misses'.

Contracts

Per-chip models from the SVD, the manual and the errata sheet, corrected on silicon. The rule is the stricter of the errata sheet and the board.

haveOver 2,000 recorded gaps and 163 errata-vs-silicon entries. ST, Microchip, Nordic, Espressif. dulsec hw path USART2 Unclocked Enabled prints the sequence with citations.

gapThe best-covered part is 78 % complete; the rest were built demo-first.

Secrets & constant time

A C project links a library written in Dulse. The compiler guarantees no branch or address depends on the secret, zeroes what it touched, and refuses a secret in a memory configuration nothing measured. verify proves the shipped bytes are the checked bytes. For C you already have, check image.elf --secret KEY follows a symbol you mark through the binary.

measuredAES-128 matches FIPS-197 on the board, 203 obligations. Flat in every memory configuration on F429, F401, L152, F746. --set CTL_BRANCH=1 gives E0901. Over a C ELF: mbedTLS's table AES with the key marked gives 70 secret-indexed lookups, and the Dulse AES comes out clean.

gapA * on a secret emits umull on an M3 and leaks; the per-part instruction table is a design. The walk loses the secret in BearSSL's bitsliced aes_ct, and no finding on a C image has been adjudicated by hand yet. Power and EM out of scope.

What a change does

For a PR to a firmware project, the register-level diff of what the board actually runs. 'Nothing hardware-visible' is an answer.

ran81 open PRs over Zephyr, RIOT, TinyUSB, Embassy, NuttX, MicroPython, Tock. RIOT 22413 changes every nRF52's UART baud value inside a PR titled as a new chip.

gapNo regression caught retrospectively yet. In our planted-PR bench a model reading the code was the better reviewer; this shows what the hardware sees, it doesn't review.

The language

The same checker over Dulse source says more, because the compiler owns the instructions: the deadlines above, DMA ownership across handlers, the MPU table from the grants.

bench0 of 7 Dulse images broke the control loop, 11 of 14 C images did. Qwen 27B: 0 of 6 in C, 7 of 8 in Dulse.

gap2 to 3x the cost per session, every session, and a frontier model didn't need it. Cells of one to five runs on the bench the model was calibrated on. The runs, and the newer rounds, are at dyno.dulse.dev.

What it doesn't find

The catch, written down.

  • Precision on vendor code: 0.020 then 0.062 per site on the first held-out corpus, 0.156 on a fresh one where the second fix wave didn't help. What it finds is real; most of what it reports on a big vendor image isn't, yet.
  • Recall: 2 of 34 historical defects, then 3 of 46, one strict. 11 of the 34 misses weren't register-rule bugs at all.
  • Walking a vendor SDK is slow. A Dulse example checks in 0.44 s at the median; the 164 pico-sdk examples took 200 s at the median and half an hour at the worst. What costs is what C is allowed to do (handlers installed at run time, ROM calls, jump tables in .data), not the size of the image.
  • The agent numbers are small and in-sample, and Dulse costs 2-3x per session.
  • A clean result is partly 'not looked at'. The coverage line is on every run for that reason.
  • Every hole closed in the agent rounds was followed by one a level up (the hollow save, a mode of the program's own, a shadow name). The checker proves what's left is safe, not that the feature is there.

Side channels and faults

Timing side channels today. Faults next, fault record first.

The memory system is a function of the address sequence and the configuration, and no language's semantics mentions either. So a program that is correct by every definition the compiler has still leaks a key, and the countermeasure people reach for when they can't go branchless, two balanced arms, fails from placement alone.

ST's X-CUBE-CRYPTOLIB gives up a full AES-128 key at the product default. The RAM section that fixes it ships in the same package, and none of its 2,277 linker scripts maps it. 8-byte alignment closes the channel and is 20-25 % faster. That is a placement property, and only something that owns the emitter and the layout can promise it.

Dulse owns both. E0907 refuses a secret computed in a memory configuration no bench capture covers, and E0908 refuses the configuration moving while the secret is live. No branch, address or information flow is involved; a source-level tool can't say it, because the configuration is a register write it never sees.

Faults: the plan, not a claim

The same shape with the part's own fault record in place of its timing record: the hardened decisions in a shipped image (TF-M FIH, GCC's hardened compares, a Dulse decision) simulated against the faults that part shows on the bench, and a ledger that names the part the claim was qualified on. So when you port, you know what you lost.

orderA fault record for one part first (a ChipWhisperer campaign at a pre-registered grid, skip / fetch-word / load / register classes). Then a three-arm baseline with no Dulse in it. Then the design. Nothing is built.
